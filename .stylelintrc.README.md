# Why these Stylelint rules are switched off

Every switch-off here is a decision, not an escape from a fix. A rule is switched off when
it describes **some other project** rather than this one — not when it is hard to satisfy.

## `selector-id-pattern` — 133 violations

The standard asks for `kebab-case` on ids, and the whole project is on `camelCase`
(`#adminNotifBell`, `#productsGrid`). And the name does not live in the CSS alone: the same
name appears in `getElementById` across 34 JS files, and in `id=` across 57 view files.

So satisfying the rule means renaming across three languages at once — a wide-risk change
for zero gain. The existing convention is consistent, and consistency is what the rule
exists to serve in the first place.

## `declaration-block-single-line-max-declarations` — 74 violations

Short rules written on one line:

```css
.hpc-tag-best { background: #6366f1; color: #fff; }
```

This is a matter of **formatting**, and it belongs to Prettier rather than Stylelint. The
division is deliberate: Prettier for shape, Stylelint for correctness. Two rules governing
the same shape collide at the first disagreement.

To normalise the formatting: `npm run format`.

## `property-no-vendor-prefix` — 11 violations

`-webkit-appearance`, `-moz-appearance` and their siblings. The rule assumes the prefixes
have become redundant, which is true of some of them and not of all — and `appearance` on
form elements is still needed in browsers people use.

Removing them needs a measurement against real browsers rather than trust in a general
rule. And until that is measured, keeping them is cheaper than breaking the look of an
input field.
